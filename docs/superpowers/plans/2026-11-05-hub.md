# Hub Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add the hub to `ari watch`: a full-terminal mode with one watch window per agent, a graph of spawns and messages, and each agent's own context window.

**Architecture:** The hook records a few more facts: spawn name/prompt, `SendMessage` recipient/text, edit line counts, and the new `PermissionRequest` event. The reducer keeps per-agent rings (recent calls, activity lanes, files, wait) and a session message log. The token ledger tracks each transcript's current context size and an estimate of what filled it. A new `hub` module draws into a ratatui `Buffer` and converts it to `Vec<Line>`, so it fits the existing `watch` frame loop unchanged.

**Tech Stack:** Rust 2024, ratatui 0.30 (`Buffer`, `Rect`, `Block`), serde_json, insta. No new dependencies.

**Spec:** `docs/superpowers/specs/2026-11-05-hub-design.md`. Mockup: https://claude.ai/artifact/HoFqkqMBRz2r1c2YyCvJRi

## Global Constraints

- Zero tokens: hooks print nothing, always exit 0, `timeout: 1`. Nothing is sent to Claude Code.
- `scripts/bench-hook.sh` stays under p95 15 ms.
- No new crates.
- Event lines stay under `MAX_LINE` (4096). New strings are truncated: names and recipients to 40 chars, prompt and message text to their first line at 160.
- `NO_COLOR` respected. Glyphs carry the meaning. `--ascii` maps every hub glyph to one ASCII column.
- Sizes: Full ≥ 160×45, Compact ≥ 120×30, else too small (spec §Sizes).
- Copy comes from the spec verbatim: `approve or deny it in the Claude Code window`, `no agents yet`, `hub needs 120×30 · this window is W×H · x panel`, `+N more`, `+N more ›`, `estimate`.
- CI: `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test`. Snapshot updates: `INSTA_UPDATE=always cargo test`, then review the `.snap` diff.
- One small commit per step that says "Commit", message style `feat:`/`fix:`/`test:`/`docs:`, ending with the attribution line.

## Review Focus

1. **Many agents** (e.g. 12 parallel Explore subagents): graph ends in a `+N more` node, table ends in `+N more`, watch windows page. Tests in Tasks 6 and 7.
2. **Resizing across size tiers** while zoomed: below 120×30 the panel shows the notice, and growing again restores the same hub screen and selection. Test in Task 10.
3. **Wide characters** (CJK, emoji) in prompts, messages and paths: every hub line is exactly the terminal width, so borders stay aligned. Test in Task 7.
4. **No subagents, or no hooks at all**: the hub draws the lead node and `no agents yet`, and the strip says what `bar::render` says. Tests in Tasks 5 and 6.
5. **Messages to names never spawned**, and protocol messages (shutdown requests): kept as written, no panic, no edge drawn. Tests in Tasks 3 and 6.

### Task 3: Reducer keeps per-agent records and the message log

**Files:**
- Modify: `src/state.rs`

```rust
pub struct CallRec { pub t: u64, pub tool: String, pub act: String, pub ok: Option<bool>, pub dur: Option<u64>, pub msg: Option<String> }
pub struct Msg { pub t: u64, pub from: String, pub to: String, pub text: String }   // from/to = agent id ("main" for the lead), or `to` as written when unknown
pub struct Spawn { pub id: String, pub by: String, pub name: Option<String>, pub kind: String, pub prompt: Option<String> }
pub struct FileRec { pub edits: u32, pub added: u32, pub removed: u32 }
// Agent gains:
pub name: Option<String>, pub parent: Option<String>, pub prompt: Option<String>,
pub recent: VecDeque<CallRec>, pub waiting: Option<(u64, String)>,
pub lane: VecDeque<(u64, u16)>, pub files: BTreeMap<String, FileRec>,
// Task gains: pub owner: Option<String>, pub blocked: Vec<String>
// State gains: pub messages: VecDeque<Msg>, pub spawns: VecDeque<Spawn>
impl Agent { pub fn label(&self) -> String }                 // "main" for id "main", else name, else kind
impl State { pub fn waiting(&self) -> Option<&Agent>;         // agent with the oldest open wait
             pub fn agent_by_name(&self, name: &str) -> Option<&Agent> }
```
- Constants: `RECENT_CALLS = 40`, `LANE_MS = 12_000`, `LANES = 50`, `MESSAGES = 60`, `SPAWNS = 16`. `CACHE_VERSION` 10 → 11.
- Rules:
  - `PreToolUse` pushes a `CallRec` (ok None) and bumps the lane. If the tool is Agent, it queues a `Spawn` (`id` = tool_use_id, `by` = aid, `kind` = ev.kind). If the tool is SendMessage with `to`, it pushes a `Msg`. `to` resolves via `agent_by_name`; `team-lead`/`main`/`lead` map to `"main"`; anything else is kept as written.
  - `PostToolUse`/`PostToolUseFailure` fill the agent's newest `CallRec` with ok None and the same tool: ok, `dur`, failure `msg`. For file tools with `lines`, they add to `files[path]`, where path = `act` without its `editing ` prefix. An Agent post removes any still-queued `Spawn` with that `id`.
  - The first event of a new agent id (in `agent_mut`) claims the oldest `Spawn` whose `kind` equals `ev.at`, else the oldest one. That sets `name`, `parent` = `by`, `prompt`.
  - `PermissionRequest` sets that agent's `waiting = Some((t, act))`. That agent's next `PreToolUse`/`PostToolUse`/`PostToolUseFailure`/`Stop`/`SubagentStop`/`StopFailure` clears it. `UserPromptSubmit` clears every wait.
  - `verdict_with` returns `NeedsYou` when `needs_you` is set or `waiting()` is Some.
  - `update_tasks` copies `owner`/`blocked` when present.

### Task 4: Token ledger tracks context size and what filled it

**Files:**
- Modify: `src/tokens.rs` (`Ledger`, `Ledger::apply`, `CACHE_VERSION` 3 → 4)

**Interfaces:**
- Produces on `Ledger`: `ctx: u64` (input side of the latest counted request), `fill: BTreeMap<String, u64>` (keys are `base`, `messages`, or a tool name), `tool_ids: VecDeque<(String, String)>` (tool_use id → name, cap `TOOL_IDS = 32`), `pending: Vec<String>`.
- Rules in `apply`:
  - The `tool_use` blocks of an assistant entry are recorded into `tool_ids` before the `message.id` dedupe returns (D14 splits blocks across entries).
  - A `user` entry's `tool_result` blocks push their tool's name onto `pending`.
  - On a counted request, `side = input + cache_write + cache_read`. If `ctx == 0` or `side < ctx`: `fill = {base: side}`. Otherwise the growth `side - ctx` is split equally over `pending` (remainder to the first), or goes to `messages` if `pending` is empty. Then clear `pending` and set `ctx = side`.
